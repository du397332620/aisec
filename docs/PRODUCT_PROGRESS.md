## 2. 一页摘要

AIsec 是面向 AI 辅助开发项目的、本地优先的安全验收 CLI 与 MCP 服务。它把待扫描项目视为不可信输入，识别资产和攻击面，运行确定性的原生检测与可选第三方扫描器，关联证据形成攻击路径，并输出覆盖状态、发布决策和受约束的修复合同。

当前仓库已经形成可运行的 `0.1.0` Beta 基础：CLI、原生检测、报告、基线复扫、修复合同、MCP、受控被动 Web 验证和 CI 配置均已落地。默认测试当前为 30/30 通过、0 跳过；真实引擎套件为 2/2 通过；生产依赖审计为 0 个已知漏洞，启动语料基准为 9 TP / 0 FP / 0 FN。

这还不是公开发布就绪状态。P0-01、P0-02 与 P0-04 已关闭：Git 基线、公开远程仓库、首次 Ubuntu/Node.js 20 CI、真实第三方引擎矩阵，以及三类公开数据契约的运行时门禁均已建立。当前最大的证据缺口转为：公开基准仍过小；尚未建立 macOS/Linux CI 矩阵；没有发布 provenance 或正式安全报告渠道。

### 与现有开源工具的关系

GitHub 上已经存在成熟的单项或分层扫描器，AIsec 不应重复实现它们的全部分析引擎：

| 项目 | 主要能力 | AIsec 的关系 |
| --- | --- | --- |
| [Opengrep](https://github.com/opengrep/opengrep) / [Semgrep](https://github.com/semgrep/semgrep) | 多语言代码模式与静态分析 | 作为通用 SAST 底座；AIsec 补充 AI 数据流、应用上下文、覆盖与裁决编排 |
| [CodeQL](https://github.com/github/codeql) | 基于代码数据库的语义查询和污点分析 | 是更深语义分析的可选替代/未来适配方向，不是当前包内依赖 |
| [Gitleaks](https://github.com/gitleaks/gitleaks) | 工作区、文件与 Git 历史秘密检测 | 已设计为可选引擎；AIsec 负责隔离配置、脱敏、覆盖和统一报告 |
| [Trivy](https://github.com/aquasecurity/trivy) | 依赖漏洞、IaC 错误配置、秘密等 | 已设计为可选引擎；AIsec 负责数据库缺口不能静默放行的验收语义 |
| [MobSF](https://github.com/MobSF/Mobile-Security-Framework-MobSF) | Android/iOS 源码与产物静态/动态分析 | 能力更深但部署和许可证边界不同；保持为用户单独管理的服务候选 |
| [OWASP ZAP](https://github.com/zaproxy/zaproxy) | Web DAST、爬取和主动扫描 | 比当前被动验证更深入；只有建立严格授权和隔离模型后才考虑适配 |

AIsec 的差异化不是“再造一个规则扫描器”，而是把这些能力放入适合 AI 编码工作流的安全验收闭环：项目盘点、证据等级、跨层攻击路径、显式覆盖缺口、稳定发布裁决、受约束修复合同和复扫验证。

## 3. 问题陈述

AI 生成或修改代码的速度，正在超过人工安全审查的速度。Web、移动端、BaaS 配置、CI、依赖和部署产物之间还存在跨层风险，单一 SAST 或依赖扫描器无法回答以下核心问题：

1. 当前项目实际包含哪些技术、入口、敏感资产和信任边界？
2. 哪些发现有确定证据，哪些只是需要人工确认的推断？
3. 预期检查是否真的执行完整，还是因为工具缺失而得到“伪干净”结果？
4. 多个低层信号能否组合成可利用的攻击路径？
5. 修复后是否真正关闭原发现，且没有引入新的高风险问题？

用户需要的不是“这段代码像不像 AI 写的”，而是在发布前得到可解释、可复现、不会掩盖覆盖缺口的安全验收结果。

## 4. 产品方案

AIsec 提供一个本地编排与证据归一层：

1. 盘点项目技术栈、资产、入口和配置。
2. 对优先支持的 Web、BaaS、移动端和 AI 数据流运行原生静态检测。
3. 在用户显式安装后调用 Gitleaks、Opengrep 和 Trivy，补充秘密、通用 SAST、依赖与 IaC 覆盖。
4. 检查 APK/IPA 中有限且高价值的配置和秘密暴露信号。
5. 将信号标记为 `verified`、`static_confirmed` 或 `inferred`，再形成发现和攻击路径。
6. 同时报告每个安全域的 `complete`、`partial`、`not_run` 或 `failed` 状态。
7. 输出 `block`、`incomplete`、`review` 或 `no_blockers_found`，以及终端、JSON、HTML、SARIF 报告。
8. 通过基线复扫和修复合同接入现有编码 Agent，但不自动修改代码。

### 产品原则

- 不判断代码作者是人还是 AI；只判断可观察的安全证据。
- 不把 `no_blockers_found` 描述为安全认证。
- 检查缺失或失败时 fail closed，不能静默降级为干净结果。
- 高危/严重问题只有在存在非推断证据时才能阻断发布。
- LLM 可以解释和协助修复，但不能提升证据等级或单独做发布裁决。
- 默认离线、本地执行，不运行目标项目代码，不自动下载扫描器。
- 网络验证必须由用户显式授权，并限制在非生产目标和非破坏性请求内。

## 5. 目标用户

- 使用 Coding Agent 构建 Web 或移动应用的个人开发者和小团队。
- 需要在合并或部署前增加安全门禁的平台与应用团队。
- 希望让编码 Agent 按证据修复、但不希望它自行扩大扫描权限的安全负责人。
- 需要统一查看 SAST、秘密、依赖、BaaS、移动端产物和被动 Web 检查结果的维护者。

## 6. 用户故事

1. 作为 AI 辅助开发者，我希望用一个命令盘点项目技术栈，以便知道接下来应该执行哪些安全检查。
2. 作为 Web 开发者，我希望检测用户输入到 SQL、命令、URL、DOM 或 React HTML sink 的危险数据流，以便在部署前修复注入风险。
3. 作为 AI 应用开发者，我希望识别模型输出进入命令、代码或数据库执行路径的情况，以便不把不可信模型输出当作指令。
4. 作为 Next.js/Node.js 开发者，我希望发现敏感路由缺少可见鉴权的信号，以便人工确认中间件和业务授权是否完整。
5. 作为 Supabase 用户，我希望检查表级 RLS 和过度宽松策略，以便减少直接数据库访问造成的数据越权。
6. 作为 Firebase 用户，我希望发现无条件允许访问的规则，以便避免数据库或存储公开暴露。
7. 作为 React Native 或 Flutter 开发者，我希望发现敏感数据存储、不安全 WebView、明文网络和 TLS 绕过，以便降低客户端攻击面。
8. 作为 Android/iOS 开发者，我希望检查 Manifest、Info.plist 和常见平台配置，以便在打包前发现弱安全设置。
9. 作为移动端发布负责人，我希望扫描 APK/IPA 中嵌入的秘密、HTTP 地址和关键安全配置，以便检查源代码与最终产物的差异。
10. 作为仓库维护者，我希望发现源码中的高价值凭据模式，并在报告中看到脱敏证据，以便撤销凭据且不造成二次泄漏。
11. 作为 CI 维护者，我希望发现 GitHub Actions 表达式注入等工作流风险，以便攻击者不能借不可信事件字段执行命令。
12. 作为安全负责人，我希望把 Gitleaks、Opengrep 和 Trivy 的结果归一到同一个模型中，以便统一做发布裁决。
13. 作为发布负责人，我希望缺少必需扫描器时结果是 `incomplete` 而不是通过，以便 CI 不会因工具故障放行。
14. 作为审查者，我希望每条发现区分已验证、静态确认和推断证据，以便把人工时间投入真正高风险的问题。
15. 作为审查者，我希望相关信号被关联成攻击路径，同时保留更强的底层发现，以便理解影响且不丢失证据。
16. 作为开发者，我希望得到包含约束和回归测试要求的修复合同，以便让编码 Agent 修复时不改变无关行为。
17. 作为开发者，我希望对修复前后的扫描做基线比较，以便区分已解决、仍存在和未重新检查的问题。
18. 作为维护者，我希望只能用带原因和到期时间的稳定指纹抑制误报，以便例外不会永久隐藏风险。
19. 作为 CI 用户，我希望使用稳定退出码和 SARIF/JSON 输出，以便把安全裁决接入自动化流程。
20. 作为人类审查者，我希望获得终端和 HTML 报告，以便快速阅读发现、覆盖和限制说明。
21. 作为 Coding Agent 用户，我希望通过只读型 MCP 工具检查项目、读取报告和验证修复，以便不授予 Agent 主动探测网络目标的能力。
22. 作为测试环境所有者，我希望在明确授权后做有请求上限的被动 GET 检查，以便验证基础响应头和 Cookie 属性。
23. 作为测试环境所有者，我希望验证器拒绝生产环境、私网/元数据目标和跨源重定向，以便降低 SSRF 与误操作风险。
24. 作为扫描器使用者，我希望目标仓库的脚本、配置、忽略文件和环境变量不能削弱扫描，以便恶意项目不能制造伪干净结果。
25. 作为工具维护者，我希望规则变更同时提供真实阳性和安全近似样本，以便持续衡量漏报与误报。
26. 作为开源使用者，我希望清楚看到工具已执行和未执行的能力边界，以便不会把局部覆盖误解成全面安全保证。

## 8. 实现决策

- 使用 TypeScript/Node.js 构建单一 CLI 包，同时导出程序化接口和 MCP stdio 服务。
- 采用“盘点 → 信号 → 攻击路径 → 发现 → 覆盖 → 裁决”的数据模型，保留原始证据来源。
- 发布裁决优先检查有证据的高危/严重发现，其次检查必需覆盖是否完整，再处理推断或中风险审查项。
- 原生检测聚焦 AI 辅助项目常见且可以确定性识别的跨层风险；广泛语言覆盖交给可选第三方引擎。
- 第三方引擎只从显式路径、散列固定的托管目录或用户 PATH 中发现；扫描期间不联网下载。
- Beta 只运行经过真实 fixture 验证的精确引擎版本；未知版本、版本探测失败或输出契约漂移均 fail closed。
- Trivy 漏洞数据库只能通过显式 setup 命令准备，扫描只使用 AIsec 数据目录中的离线、有效且未过期 schema-v2 缓存。
- 所有目标仓库内容、归档内容和第三方引擎输出均视为不可信；AIsec 自带规则和用户显式配置视为可信。
- 移动产物只做有界、选择性的静态读取，不在磁盘上解压，也不执行其中内容。
- Web 验证仅允许 `local`、`test`、`staging`，需要授权清单和命令行确认，只发送有上限的 GET 请求。
- MCP 不暴露 Web 验证入口，避免 Agent 自主向目标发送网络请求。
- 修复动作交给既有编码 Agent；AIsec 只给出证据、约束、测试要求和复扫命令。
- 报告用稳定 schema 版本和稳定退出码接入 CI；覆盖不完整不能等价于通过。
- 公开 Schema 是运行时数据契约的唯一事实源；未知版本、未知字段和无效嵌套值在 CLI/MCP/持久化边界 fail closed。

## 9. 测试与验收决策

优先验证用户可观察的最高层行为，而不是内部实现细节：

1. **CLI seam**：命令参数、退出码、报告生成和错误语义。
2. **扫描编排 seam**：从真实 fixture 到信号、攻击路径、覆盖和最终裁决。
3. **修复闭环 seam**：基线报告、修复合同、复扫和未重新检查状态。
4. **不可信输入 seam**：符号链接、无效/恶意归档、目标控制的抑制、环境变量和引擎篡改。
5. **MCP seam**：真实 stdio 消息交换和允许暴露的工具集合。
6. **Web seam**：本地 HTTP 服务、请求上限、授权边界、DNS/重定向约束。
7. **发布 seam**：从 lockfile 安装、构建、测试、基准到实际 npm 包安装后的 CLI smoke test。
8. **真实引擎 seam**：固定版本的 Gitleaks、Opengrep、Trivy 对恶意抑制 fixture 和安全近似 fixture 做端到端验收，并对每个适配器注入进程失败、超时和畸形输出。

每条新检测规则至少需要一个脆弱样本和一个不会触发的安全近似样本。测试必须确认报告脱敏、证据等级、覆盖状态和裁决，而不只确认“出现了某个字符串”。

## 14. 主要风险

| 风险 | 影响 | 当前缓解 | 后续动作 |
| --- | --- | --- | --- |
| 用户把局部扫描当成全面认证 | 形成错误安全感 | 明确覆盖状态、裁决词和免责声明 | 在所有报告格式保持同等醒目的限制说明 |
| 启动语料过小造成虚高指标 | 误判检测质量 | 基准输出自带警告 | 扩大独立、按类别审阅的语料，不使用总分掩盖薄弱类别 |
| 第三方解析器处理恶意仓库时存在漏洞 | 扫描器自身被攻击 | 不执行项目、子进程限制、配置隔离 | 增加 OS 沙箱运行指南和对抗 fixture |
| 外部漏洞数据库缺失或过期 | 依赖检查伪完整 | 显式准备；记录 schema/freshness；缺失、空、无效、过期均标记 failed/incomplete | 后续增加组织镜像、数据库来源证明和自动化刷新策略 |
| 静态推断产生误报或漏报 | 降低信任或漏过风险 | 证据分级、近似阴性、抑制到期 | 按规则跟踪真实反馈和适用框架版本 |
| Web 验证越权或形成 SSRF | 法律与基础设施风险 | 明确授权、非生产限制、DNS 固定、同源重定向 | 动态能力扩大前单独做威胁建模和安全评审 |
| 发布包或 CI 供应链被篡改 | 用户执行恶意扫描器 | 固定 Action、lockfile、无 lifecycle scripts | 增加 provenance、SBOM、签名与最小权限发布 |
| 跨平台 CI 矩阵尚未建立 | 当前只证明 Ubuntu/Node.js 20 远程运行与 macOS/Node 22 本地运行 | 首次 GitHub Actions 已成功，Action 固定到提交 | 增加 macOS/Linux 与约定 Node 版本矩阵和打包安装 smoke |
